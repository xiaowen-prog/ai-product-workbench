# AI 产品工厂产品需求基线

状态：候选草案，等待用户确认，不得作为最终实现约束

锁定日期：2026-11-20

## 一、产品目的

把老师项目的完整需求澄清与 PRD 流程，和后端开发、验收、预览、试用、反馈、V2 流程串成一个完整 AI 产品工厂。

用户只面对一个产品入口。需求澄清产出的 PRD 和方案必须成为后端开发的直接输入。

## 二、不可改动的产品要求

### 两个老师项目的职责和维护源

- 项目一是 `agent-workshop`，源码来源为 [https://github.com/hubooooooo/agent-workshop](https://github.com/hubooooooo/agent-workshop)。它负责需求澄清、PRD、领域建模、组件选型、架构方案、独立审稿、待确认问题和交接包。
- 项目二是 `idea-to-launch-kit`，源码来源为 [https://github.com/hubooooooo/idea-to-launch-kit](https://github.com/hubooooooo/idea-to-launch-kit)。它负责接收项目一的 PRD 和交接材料，执行后端开发、API、数据模型、任务、Swagger/OpenAPI、权限约束、测试、验收和运行状态。
- 项目一的交接包必须作为项目二的开发输入，两个项目要串成一条产品链路，不得用当前项目里简化的 FastAPI 状态模型替代项目二的开发实现。
- 项目二原有的 Swagger/OpenAPI 文档、路由、请求响应 schema、权限约束、错误格式、任务状态、测试和验收规则必须完整保留。
- v29 只作为融合后的产品前端视觉层，不能替换两个老师项目原有的后端契约和开发规则。
- 两个老师项目中发现的小 bug 可以修复，但修复必须保持原有 API 契约、Swagger/OpenAPI 约束和流程语义，并留下可回溯的修复记录。

### 需求澄清

- 需求澄清必须保留老师版本的完整多轮逻辑，不能人为压缩成固定的四个问题。
- 问题数量由当前需求缺口决定，但必须覆盖目标、用户、核心闭环、交付物、边界、约束和成功标准。
- 每一轮问题都要支持 A、B、C、D 等推荐选项、直接点击、自由输入和“帮我想想”。
- 用户明确回答过的内容必须进入当前需求事实，后续模型不得重新当作未知项提出。
- 用户选择“按推荐”属于明确决策，不能在下一轮被模型改写成相反方向。
- 用户回答“不确定”时才可以保留为待确认项，系统不能替用户补造结论。

### PRD 与方案

- 需求澄清必须产出 PRD，并把 PRD 直接交给方案和后端开发阶段。
- 方案必须包含产品定位、核心闭环、MVP 范围、边界、验收标准、API、数据模型、测试和降级策略。
- 独立审稿必须使用真实模型完成，分数必须达到 80 分。
- 分数必须有稳定、可解释的规则约束。模型自由打分不能单独决定是否通过。
- 存在未解决的高风险或会改变 MVP 的中等问题时，不能显示为审稿通过。
- 审稿意见写明“修复后放行”时，系统必须继续停留在修改状态，不能进入后端开发。

### 后端开发与验收

- 需求、PRD、方案、后端开发、后端验收、预览验证、试用反馈和 V2 必须使用一套状态机。
- 后端开发阶段必须产生可检查的 API、数据模型、测试计划和本地可运行预览。
- 后端验收未通过时不能打开产品预览。
- 预览必须通过页面、健康检查和核心动作验证后，才能开始试用。
- 必须先开始试用并保存非空反馈，才允许创建下一版。
- V2 必须是独立项目，保留 V1，并保留 `parent_id`、`root_id` 和首次 `affected_area` 逻辑。

### 视觉与入口

- 正式前端使用 v29 Blue / Print Studio 视觉，保留墨蓝导航、明亮工作区、钴蓝重点、输入区、问答样式、进度轨、预览样式和移动端修复。
- 正式本地入口是 `dist/` 通过本地 FastAPI 服务提供的页面。
- 直接打开 `dist/index.html` 只属于离线示例，不能作为真实 API 入口。
- 不重新设计界面，不因接入后端替换成另一套视觉。

### 后端与密钥

- 真实模型 Key 只能由后端读取和保存。
- Key 不能写进前端、localStorage、产品数据或源码包。
- API 使用同源相对路径，不写死测试端口或外部环境域名。
- mock 只能用于离线示例，不能冒充真实模型、真实后端或真实验收。

### 发布范围

- 本阶段只改本机项目。
- 未经另行授权，不提交、推送、合并、部署 GitHub 或腾讯云。
- 不覆盖后端之外的用户数据，不清空 localStorage，不删除既有项目。

## 三、当前唯一实现基线

- 正式页面入口：`dist/index.html`
- 正式前端脚本：`dist/app.js`
- 正式样式：`dist/app.css`
- 正式业务状态机：待融合 `idea-to-launch-kit` 的开发项目源码和 API 契约
- 当前 `backend/app/`：临时本地状态适配器，不得替代老师开发项目
- 正式 API 前缀、Swagger/OpenAPI 文档和请求响应 schema：以 `idea-to-launch-kit` 源码为准，待融合后回填准确路径
- 本地启动入口：`tools/start-local-v29.sh`
- 本地服务地址：`http://127.0.0.1:8770/`
- 老师引擎副本：`.local/teacher-engine/`，只作为参考源码，不作为正式网页入口

任何人或任何模型都不得在没有用户明确确认的情况下更换上述维护源、入口或状态机。

## 四、禁止重复发生的问题

- 不能在老师引擎和原 FastAPI 后端之间来回切换，造成已确认流程被重写。
- 不能把用户已经确认的需求重新当作模型待确认项。
- 不能用固定四题替代完整需求澄清。
- 不能用 localStorage 的临时标记代替后端验收状态。
- 不能把“交接包已生成”写成“后端代码已完成”。
- 不能把“模型返回了 80 分”直接写成“方案通过”。
- 不能用一次测试项目或旧截图替代当前正式入口验收。

## 五、变更规则

任何后续修改必须先回答四个问题：

1. 修改影响了哪一条锁定需求。
2. 是否改变正式入口、维护源或 API 契约。
3. 是否会让已经确认的用户决策重新变成待确认。
4. 是否需要用户重新确认。

只要答案涉及锁定需求、正式入口、维护源、状态机或验收门禁，先暂停实现并请求用户确认。

## 六、验收基线

- `node --check dist/app.js` 通过。
- 后端测试通过。
- 需求澄清存在推荐选项和自由输入。
- 用户回答会持久化到后端项目状态。
- 方案审稿分数稳定且至少 80 分。
- 未通过门禁时没有进入后端开发的按钮。
- 后端验收、预览验证、试用反馈和 V2 能通过同一个项目 ID 链路完成。
- 桌面 1280、手机 390 和 320 宽度没有横向溢出、文字重叠或按钮裁切。
